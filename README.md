# Watch Party

A browser-based watch party application that lets people join a shared room and synchronize video playback. Built with Python, FastAPI, WebSockets, FFmpeg, and vanilla JavaScript.

I started this project after running into delays and poor video quality while watching with a friend through screen sharing. The goal was a shared viewing experience with individual browser players and coordinated play, pause, and seek controls.

## Features

- **Shareable rooms:** Create a room from a direct video URL and invite another viewer through a room link.
- **Synchronized playback:** Exchange playback events over WebSockets and maintain a shared timeline on the server.
- **Clock and drift correction:** Estimate the server clock using ping/pong timing, then adjust playback speed or seek to bring viewers back toward the shared timeline.
- **Browser-friendly video:** Convert video to H.264 and audio to AAC, served through HLS with a target segment duration of three seconds.
- **Change videos in place:** Load another source while keeping the same room and notifying connected viewers.
- **Player controls:** Seek, adjust volume, toggle fullscreen, and manually resynchronize playback.
- **Diagnostics:** Health endpoint, Prometheus-style counters, helper unit tests, and a GitHub Actions test workflow.

## How it works

```text
Browser players <---- WebSocket playback events ----> FastAPI room state
       |                                                 |
       +---- HLS manifest and segment requests ----------+
                                                         |
                                                  FFmpeg process
                                                         |
                                                 Direct video URL
```

The server stores each room's playback position, play/pause state, and timestamp. Clients use that timeline and an estimated clock offset to calculate where playback should be. Ping samples are collected every three seconds; the lowest-latency sample among the most recent twelve is used for the offset estimate. The player corrects drift through temporary playback-speed adjustments or seeking.

Each room starts an FFmpeg process that writes an HLS playlist and media segments to a temporary directory. The frontend uses hls.js where supported, with native media playback as the alternative. If FFmpeg is absent, the server uses a direct proxy path; that path cannot convert incompatible codecs.

## Run locally

### Requirements

- Python 3.11 or newer (the tests use Python 3.11's `datetime.UTC`).
- macOS for the current transcoding configuration, which uses Apple's `h264_videotoolbox` encoder.
- FFmpeg and ffprobe available on your `PATH`.
- A browser and a direct, accessible video URL. A webpage containing a video is not a direct media URL.

On macOS with Homebrew:

```bash
brew install ffmpeg
```

From this project directory:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m uvicorn server:app --host 127.0.0.1 --port 8000
```

Open **http://localhost:8000**. Run the command from the project root because static files are resolved relative to the working directory.

### Try a room

1. Paste a direct video URL that you have permission to share and create a room.
2. Open the room link in two browser windows.
3. Allow time for the first media segments to become available and click play if the browser blocks autoplay.
4. Play, pause, or seek in one window and observe the other.
5. Use the player's Sync control to request the current room timeline if needed.

Seeking ahead of the generated segments can buffer. Actual synchronization depends on network conditions, decoding, and buffering; the repository does not include an end-to-end synchronization benchmark.

### Share with a remote viewer

The optional script entry point automatically attempts to create a Cloudflare Quick Tunnel when `cloudflared` is installed:

```bash
brew install cloudflared
python server.py
```

Use the public room link generated by the application. Keep the host computer and server running during the session. The public address is temporary. Starting through Uvicorn, as in the local instructions, does not launch a tunnel.

## API overview

| Route | Purpose |
| --- | --- |
| `POST /api/create` | Create a room with `stream_url` and an optional `title`. |
| `GET /api/room/{room_id}` | Read playback state, media URL, title, and preparation estimate. |
| `GET /api/config` | Read the public tunnel URL, if available. |
| `WS /ws/{room_id}` | Exchange sync, ping/pong, playback, and video-change messages. |
| `GET /hls/{room_id}/out.m3u8` | Fetch the generated HLS playlist. |
| `GET /hls/{room_id}/{segment}` | Fetch a generated media segment. |
| `GET` / `HEAD /stream/{room_id}` | Proxy source media when FFmpeg is absent. |
| `GET /health` | Check application response, FFmpeg detection, and room count. |
| `GET /metrics` | Read room, WebSocket, stream-change, and proxy-error counters. |

```bash
curl http://localhost:8000/health
curl http://localhost:8000/metrics
```

The health endpoint reports whether FFmpeg was found, not whether a particular source can be transcoded.

## Tests

```bash
python -m pytest -q
```

The four existing unit tests cover relative HLS URL rewriting, a latency-offset helper, construction of a valid Pydantic playback event, and metric output. GitHub Actions runs the tests on pushes and pull requests using Python 3.11. These tests do not exercise browser playback or FFmpeg.

## Current limitations

- **Prototype deployment:** Rooms and metrics live in process memory and reset when the server restarts. Use a single server process; there is no shared database or multi-worker coordination.
- **Trusted participants:** There is no authentication or room-owner permission model. Connected participants can control playback and change the video. Source URLs are not restricted, so this version should not be operated as an unrestricted public service.
- **Media compatibility:** Sources must be directly accessible to the host. There is no integration for authenticated or DRM-protected streaming websites, and subtitles are excluded from transcoding.
- **macOS encoder:** The included Linux Dockerfile packages FFmpeg, but the current `h264_videotoolbox` command does not work in that Linux image. A compatible encoder configuration is needed before using Docker for transcoding.
- **Progress estimates:** Preparation progress is time-based, and process exit is currently treated as completion without distinguishing success from failure.
- **Resource lifecycle:** Changing a video cleans up the previous room media. There is no automatic expiry for idle rooms or complete shutdown cleanup for room media.
- **Validation coverage:** `PlaybackEvent` and `estimate_sync_offset` have unit tests but are not wired into the live WebSocket handler. Browser synchronization uses its own clock-estimation logic.
